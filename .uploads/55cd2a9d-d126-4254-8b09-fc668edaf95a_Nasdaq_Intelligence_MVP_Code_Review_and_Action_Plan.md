## 1. 项目背景与目标

项目已经部署了每日运行的追踪任务，服务入口：

- `http://47.94.225.66:8040/`

当前实现方式已经确认：

- 完全使用 Python 实现定时任务。
- Python 直接调用大模型 API。
- 暂不引入 Dify 等 Agent 工作流平台。
- 日报交付形式为 Markdown。
- 优先采用免费或低成本的数据源与技术方案。

### 1.1 原始产品目标

建立一个可以长期使用的 AI 情报产品，每日追踪纳斯达克市值前十公司，重点覆盖：

1. **科技情报**：AI、技术突破、产品发布、研发进展、芯片、云计算、技术战略、竞争格局。
2. **资本市场情报**：股价、财报、估值、投资、并购、融资、资本开支、重大市场事件。

系统需要完成：

`数据采集 → 清洗去重 → 分类 → 重要性评估 → 事件影响分析 → Markdown 日报 → 历史存储`

目标不是简单汇总十家公司的新闻，而是识别真正重要的事件，解释其意义，并提供可追溯的信息来源。

## 4. 必须优先修复的代码问题

### P0-1：行情快照与收盘价口径混淆

审查发现，代码直接读取 FMP Quote 的 `price` 和时间戳，但 Apple 报告将其表述为某交易日收盘价。

报告中的快照时间：

`2026-10-29T16:28Z`

2026 年 10 月 29 日美国处于夏令时，16:28 UTC 对应纽约时间 12:28，仍在正常交易时段。因此不能将该时点的价格直接称为当日收盘价。

**修正要求：**

明确区分以下字段：

- `current_price`：最新行情价格；
- `previous_close`：前一交易日收盘价；
- `daily_close`：指定交易日历史日线收盘价；
- `quote_timestamp`：实际行情快照时间；
- `market_status`：交易中、已收盘或休市。

如果日报需要展示上一交易日收盘价，应从历史日线接口读取对应交易日的 `close`，不能把盘中 `quote.price` 标记为收盘价。

验收要求：

- 每个价格字段具有清楚的口径和时间戳；
- 盘中价格不得标记为收盘价；
- 历史日线日期与交易日历一致；
- 报告明确说明价格对应的市场时间。

### P0-2：立即轮换已暴露的 API Key

上传的 ZIP 包含 `.env`，其中存在非空的 `FMP_API_KEY`。

**修正要求：**

1. 立即在 FMP 管理后台轮换该 Key。
2. 检查服务器、代码仓库和其他部署位置是否仍在使用旧 Key。
3. 后续交付只提供 `.env.example`，不提供真实 `.env`。
4. 确保 `.env` 被 Git 忽略。
5. 日志不得打印完整 API Key。
6. 检查公网管理页面是否存在身份认证和访问控制。

注意：不要在任何报告、代码示例或提交记录中复述真实密钥。

### P1-1：API 请求重试和错误分类

当前请求失败后直接抛出异常，建议增加有限重试机制。

建议：

- 最大重试次数：3 次；
- 指数退避，例如 2 秒、4 秒、8 秒；
- 对 HTTP 429 优先遵循 `Retry-After`；
- 对 HTTP 5xx、网络超时等临时错误进行重试；
- 对无效 API Key、权限错误、参数错误等永久错误不进行无意义重试；
- 超过重试次数后记录失败，并允许主流程按模块降级或继续其他公司任务。

### P1-2：增加缓存和增量更新

不要每天重复拉取不变的数据。

建议数据更新策略：

| 数据类型 | 更新策略 |
|---|---|
| 最新行情 | 每个交易日更新 |
| 历史行情 | 增量更新 |
| 公司概况 | 每周更新或检测到变化时更新 |
| 财务报表 | 新财报披露后更新 |
| 新闻事件 | 每日采集；如有需要可一天多次 |
| 公司名单 | 定期动态更新，并保存名单快照 |

缓存应记录数据来源、采集时间、数据日期和更新时间。

### P1-3：增加数据质量校验

建议检查：

- 股票代码是否与请求对象一致；
- 数据日期是否处于预期范围；
- 关键数值是否为空或异常；
- 财务报表币种是否一致；
- 财报季度是否连续；
- 新闻是否重复；
- TTM 是否由最近四个已披露财季正确计算。

TTM 不应简单取最近四个自然季度；应基于最近四个已披露季度，并考虑财报披露时间和数据完整性。

### P1-4：统一日期和时区

建议统一：

- 系统采集时间：UTC；
- 美股交易日期：`America/New_York`；
- 日报展示时间：`Asia/Shanghai`；
- 交易日判断：使用美股交易日历。

不得仅依赖服务器的 `date.today()` 判断美股交易日。必须考虑周末、美国市场节假日、夏令时和盘前盘后时段。

## 5. 目标技术架构

已确认当前选择 **纯 Python + 大模型 API**。现阶段不引入 Dify，也不需要多 Agent 架构。

### 5.1 架构原则

- Python 控制流程和确定性逻辑；
- LLM 负责理解、分类、重要性判断和影响分析；
- 不让 LLM 负责调度、数据计算、去重和存储等确定性任务；
- 所有重要判断尽可能有来源证据；
- 优先保证 MVP 简单、可测试、低成本；
- 先打通端到端链路，再逐步增强。

### 5.2 建议工作流

```text
Python Scheduler
       |
       v
获取纳斯达克市值前十公司名单
       |
       v
数据采集
  |              |
  v              v
金融数据       科技/公司新闻
  |              |
  +-------+------+
          |
          v
Python 数据处理
清洗、去重、时间标准化、校验
          |
          v
LLM 分析
  1. 新闻分类
  2. 重要性评估
  3. 事件影响分析
  4. 公司/行业趋势总结
          |
          v
Python 汇总和 Markdown 生成
          |
          v
SQLite + Markdown 历史存储
          |
          v
运行日志、状态和失败告警
```

### 5.3 Python 与 LLM 职责边界

| 工作 | 实现方式 |
|---|---|
| 获取公司名单 | Python |
| 采集股票行情 | Python |
| 采集新闻和公告 | Python |
| 新闻清洗 | Python |
| 新闻去重 | Python |
| 计算涨跌幅 | Python |
| 新闻分类 | LLM |
| 重要性评级 | LLM |
| 事件影响分析 | LLM |
| 趋势总结 | LLM |
| Markdown 报告生成 | Python 为主，必要时 LLM 辅助 |
| 定时调度 | Python Scheduler / Cron |
| 历史存储 | SQLite |

### 5.4 为什么不采用多 Agent

当前 MVP 不建议拆分多个自主 Agent。

建议使用一个统一的 LLM 调用封装，根据任务使用不同 Prompt 或结构化输出：

- 新闻分类；
- 重要性评估；
- 事件分析；
- 每日趋势总结。

新闻应先由 Python 清洗、去重和过滤，再按公司或主题批量提交给 LLM，避免每条新闻单独调用，控制 Token 成本。

## 7. 每日情报报告设计

### 7.1 报告与公司基本面分析分层

目前 Apple 深度报告包含大量财务指标，适合作为公司基本面档案，不适合每天对十家公司重复生成。

建议分成两类：

1. **每日情报日报**：聚焦当天发生的事件、重要性、影响和后续观察。
2. **公司基本面档案**：保留深度财务分析，按财报披露或定期更新。

### 7.2 新闻分类维度

至少覆盖：

- AI 与模型；
- 芯片与基础设施；
- 产品与技术发布；
- 研发与技术突破；
- 公司战略；
- 投资、并购与合作；
- 财报与业绩；
- 股价与估值；
- 监管与诉讼；
- 竞争格局。

### 7.3 事件重要性评级

建议采用四级：

| 等级 | 定义 | 示例 |
|---|---|---|
| S | 重大事件 | 重大战略调整、颠覆性技术突破、重大监管事件 |
| A | 高价值事件 | 新产品发布、重大投资、重要财报 |
| B | 一般事件 | 常规产品更新、一般合作消息 |
| C | 低价值信息 | 普通转载、低价值市场噪声 |

每日摘要重点展示 S、A 级事件；B 级可按公司汇总；C 级通常不进入主报告。

### 7.4 每条重要事件的分析要求

不能只复述新闻标题。至少回答：

1. 发生了什么？事实是什么？
2. 技术上有什么变化或突破？
3. 对公司产品、商业模式或战略有什么影响？
4. 对竞争对手或行业有什么影响？
5. 是否可能影响资本市场预期？
6. 后续需要观察什么？

必须明确区分：

- 来源明确支持的事实；
- 来源中的观点或预测；
- LLM 基于事实作出的推断。

不能把推断写成已经发生的事实。重要事件必须附原始来源链接、来源名称、发布时间。

### 7.5 建议的日报结构

```markdown
# Nasdaq Top 10 科技与资本情报日报
- 报告日期：
- 数据截止时间：
- 覆盖公司：
- 数据来源：
- 运行状态：

## 一、今日核心情报
- 今日最重要的 3～5 条事件
- 每条包含重要性、涉及公司、事实摘要、影响分析、来源链接

## 二、公司动态
### 公司 A
- 科技动态
- 资本市场动态
- 今日重要事件
- 后续观察

### 公司 B
...

## 三、行业趋势与竞争格局
- 跨公司技术趋势
- 竞争关系变化
- 资本投入与市场信号

## 四、市场表现
- 指定交易日收盘数据
- 涨跌幅
- 重要异常及可能原因
- 明确数据口径

## 五、后续观察清单
- 待验证事项
- 即将发布的产品、财报或重大事件

## 六、数据质量与运行说明
- 采集成功/失败情况
- 数据源覆盖情况
- 可能存在的信息缺口
- 报告生成时间
```

## 10. 给执行智能体的具体工作指令

请按以下步骤开展工作。

### Step 1：先审查完整项目，不要立即改代码

- 获取服务器当前实际运行的完整 Python 项目。
- 阅读入口、调度器、数据采集、LLM 调用、Prompt、报告生成和存储模块。
- 检查依赖、环境变量、部署配置和日志。
- 绘制当前实际工作流。
- 将已实现、部分实现、未实现、存在风险的功能逐项列出。
- 所有结论必须有代码文件和函数作为依据。
- 不要将“ZIP 未包含”错误表述成“服务器没有”。

### Step 2：对照本任务书做差距分析

输出：

- 原方案要求；
- 当前实现；
- 差距；
- 影响；
- 修正建议；
- 优先级；
- 涉及文件和函数。

### Step 3：先处理 P0

- 处理已暴露 API Key；
- 修复行情数据口径；
- 修复时间和交易日问题；
- 增加必要的数据校验。

在修改之前备份现有代码。不得在未经确认时覆盖生产环境。

### Step 4：逐步补齐新闻情报主链路

先选择少量公司和有限新闻源完成端到端验证，再扩展到十家公司。不要一开始就接入大量新闻源或构建多 Agent。

### Step 5：验证成本和质量

- 记录每次 LLM 请求的模型、耗时、Token 和成本（若供应商提供）。
- 测试批量分析与失败恢复。
- 对新闻分类、重要性评级和影响分析建立人工抽样集。
- 运行至少 7 天观察稳定性。

### Step 6：交付

最终交付：

1. 代码审查报告；
2. 差距分析表；
3. 修正后的代码；
4. 数据库结构说明；
5. Prompt 文档；
6. 日报样例；
7. 测试结果；
8. 部署和回滚说明；
9. 未完成事项及后续计划。

### 执行约束

- 不要为了架构整洁而进行大规模重写。
- 不要无理由引入 Dify 或多 Agent。
- 不要将 API Key、密码或其他密钥写入源码。
- 不要把盘中行情当成收盘价。
- 不要让 LLM 编造来源、时间、数字或事件。
- 不要把 AI 推断写成新闻事实。
- 不要仅以“脚本运行成功”作为验收。
- 先确保最小完整链路可靠，再扩展功能。

## 12. 最终产品判断

目前已有的 FMP 金融数据采集和 Apple 财务分析报告是可复用的基础，不需要推倒重来。

真正需要补齐的是科技新闻和公司事件的采集、筛选、分析与每日交付链路。

最终目标不是做一个每天罗列新闻的机器人，而是建立一个能够回答以下问题的长期情报产品：

- 今天纳斯达克头部公司发生了什么重要变化？
- 哪些技术进展可能改变竞争格局？
- 哪些资本市场信号值得关注？
- 这些事件对公司和行业意味着什么？
- 接下来应该持续观察什么？

**开发原则：保留已有成果、先打通最小完整链路、用数据和人工评估验证质量，再逐步扩展。**
